- **Question:** do MakeHuman's CC0 body targets carry onto the realistic topology well enough to be the body parameters? A spike agent worked in its own worktree (`co5-makehuman-spike`); nothing of it is in the engine.

## 2026-11-14: Stage 3, CO3, the runtime applier

- **Order:** CO3 before CO2. The capture (CO2) draws a character *from a description*, which needs the applier, so `co2-qa-harness` is branched from `co3-applier`, which is branched from Stage 2's branch (#406, not merged yet). CO4 started at the same time in Agent 1's worktree.
- **Agents:** the lead wrote the applier (`assets`, `avatar`, `anim`, `core`, `gameplay/description.rs`, `scene`, `project`) and its tests. Two helpers worked in the lead's checkout on files of their own: one built the script API (`gameplay/description_system.rs`, the definitions and `docs/scripting/api-character.md`), one synced the crate guides, topic docs and wiki. The lead read both hand-backs against the code and acted on what they found (below).
- **What it does:** `Humanoid:ApplyDescription` (and `gameplay::description::apply_description` for Character Studio's preview and the capture) makes a character look like a description: the base model's body and parts and one part per item, each drawn from a **derived model** with the identity baked in ([ADR-0038](../../../wiki/Architecture/Architecture-Decisions/ADR-0038-Identity-Is-Baked-Into-Derived-Models-Named-By-MeshId.md), proposed); the frame's bone offsets after the clips; body slider attributes; material values that modulate (`Mat_…` attributes, read by `scene`); the description kept in the character and applied again after a load or replication (`DescriptionSync`). The contract's sections 7, 10, 14, 15, 16 and 17 in [architecture.md](architecture.md) say exactly what.
- **Decided while building** (the contract said "bones move after the pose"; it didn't say what that does to a mesh): a mesh that has the parameter's shape is re-seated, a mesh that doesn't is carried (architecture §7 rule 8). So in the engine the feminine frame's eyeballs and teeth now go with their bones, which nothing did before CO3 (the Stage 1 note "leaning a file's shape by hand moves the face but not the eyeballs"). A derived model is named by `MeshId` (ADR-0038), so no model lookup changed.
- **Done when** (plan): *a character file applied in the player matches the workspace*: `editor` `a_character_file_applied_in_a_game_matches_the_workspaces_preview` (same parts; every corner of every part within 0.2 mm, in the same pose, for a heavy muscular look with a bob and no jacket). *Parts follow the build in a game*: `player` `applied_parts_have_the_bodys_identity_baked_in_and_follow_its_live_shapes` (the jacket's rest mesh is the base's `Build_Heavy` shape to 0.1 mm; lashes blink with the lid). *Masculine/feminine works*: `the_frames_bone_offsets_move_the_skeleton_and_carry_the_eyes` (joints at the manifest's offsets to 0.1 mm, the skin moved by the shape alone, the eyeballs moved and scaled with their bones), and the in-engine sheets of both frames (CO2).
- **Red, then green:** `avatar`'s five `resolve` tests ran against a stub first (`40 tests run: 35 passed, 5 failed`), then `40 passed`. The script API's tests ran red against stubs (`7 tests run: 0 passed, 7 failed`; `3 tests run: 0 passed, 3 failed`: "SetParameter is not a valid member of HumanoidDescription"). `an_applied_character_with_nothing_playing_still_wears_its_parts` was written after the first capture showed the defect and failed before the fix. The `assets` bake tests and the first six player tests were written with the code, not before it; to check they test something, three were run with the behaviour switched off (no `settle`, no follower shape weights, no `modulate`): `6 tests run: 3 passed, 3 failed`, each for its own reason.
- **Found by looking, not by tests:** the first in-engine capture drew a bare body with its clothes, hair and eyes in a heap at its feet. With no state machine the Animator posed nothing, so nothing placed the parts. Every test had passed, because every test's character idled. Fix: an Animator with nothing to play poses a body that has parts at rest, and the applier gives a body with no Animator one. This is what the quality gate is for.
- **From the helpers' review, fixed:** nothing wrote the character library into a project (now `add_default_humanoid` does, so new character projects and Insert > Character have it); stale body sliders from another base model are set back to 1; `player`'s `avatar` dependency is a test dependency. **Left, and written down:** registered identities are kept for the run (ADR-0038); `modulate` reads `tint`, `iris_tint` and `roughness_scale` only until CO7.
- **Limits** (in the wiki's Known limitations): Character Studio's workspace still writes format 1 and poses its own preview (CO12); the editor's edit mode doesn't apply kept descriptions, so a saved applied character shows its base meshes there until Play (CO13); a project made before CO3 gets the library from Insert > Character; binding and socket items have no content yet (CO9, CO10).
- **Dependencies added:** none (`gameplay` and `project` now depend on `avatar`; `player` in its tests).
- **Checks:** `cargo fmt --all`; `cargo clippy --workspace --all-targets -- -D warnings` clean; `cargo nextest run --workspace --no-fail-fast`: 4875 tests run, 4874 passed, 1 failed (`mesh-edit`'s 500k-triangle sculpt timing test, under the whole suite's load with Agent 1's Blender builds running; it passes run alone); doc tests pass; `python scripts/check-wiki.py`: 0 errors.
